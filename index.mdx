Clarwiz turns a request like "create an incident report for Rachel at ABC Dental" into browser actions in Ariya. This playbook is the map. Every page covers one area of the app and lists **recipes**: numbered click paths with the exact labels on screen, the signal to wait for after each step, how to tell success from failure, and where a human must approve.

## The task loop

Run every task through these seven steps.

1. **Parse the request.** Pull out the intent (create, find, update, send…), the object (document, client, case…) and the entities (client name, person, dates, amounts).
2. **Find the recipe.** Look the intent up in the [Task router](/start/task-router). It points to a page and a recipe heading.
3. **Check the account and the risk.** The recipe header gives its **Risk** tags and **Roles**. Use the Operator account unless the recipe needs the Principal. If any step is `EXTERNAL` or `DESTRUCTIVE`, plan the approval stop now. See [Operating rules](/start/operating-rules).
4. **Collect the inputs first.** Each recipe lists **Inputs from Clarwiz**. For documents, [Choosing a template](/documents/choosing-a-template) and the [Template catalog](/documents/template-catalog) list the facts each document needs. Ask the user for anything missing before you open the browser.
5. **Hand the recipe to the browser agent.** Pass the base URL, the recipe steps and the inputs.
6. **Execute and verify step by step.** After each action, wait for the step's `Wait for` signal. When the recipe ends, check its **Done when** signal. On an error, use the recipe's failure table.
7. **Report.** Return the outcome, the URLs of anything created, what changed, downloaded files, open items and screenshots, as listed in [Operating rules](/start/operating-rules#what-to-report-back).

## How to read a recipe

| You see | It means |
|---|---|
| **Send** | Exact visible text of a button, link, tab, heading or menu item. Match it literally. |
| `{clientSlug}` | A value you fill in. In URLs it is the ID or slug, not the display name. |
| (button, aria-label "Close") | The element type and the attribute to find it by when it has no visible text. |
| visual: top-right of the preview | Where it sits on screen, for screenshot-based agents. |
| Wait for: | What must appear or change before the next step. |
| **Done when:** | The signal that the whole recipe succeeded. |
| `READ` `WRITE` `AI` | Allowed without asking. |
| `EXTERNAL` `DESTRUCTIVE` | Stop and get approval before that step. |

## Example: "Create an incident report for Rachel at ABC Dental"

1. Router → [Create a document](/documents/create-a-document). Risk `WRITE` `AI`, so no approval is needed. Operator account.
2. Inputs: the [catalog entry](/documents/template-catalog) for **HR Incident Report** (`hr-incident-report`) lists the facts the assistant will otherwise ask for: incident date and time, location, employees involved, witnesses, what happened, action taken at the scene, injuries, police or emergency services, and who completed the report. Get them from the user first.
3. Browser: open `/documents`, pick the client in **Select a client…**, type one message holding every fact, click **Send**.
4. Wait until the message box is enabled again. Read the outcome: a draft in **Live preview**, a **Blockers** card to answer, or a red error.
5. Click **PDF (editable)** and wait for the "editable PDF downloaded" toast.
6. Report the chat URL, the document URL (from **Open in editor**), the file name and any gaps the assistant flagged.

## Scope and accuracy

- Written from the Ariya source code (`packages/web`, `packages/transport-api`, `packages/core`, `packages/shared`), not from screenshots. Labels are copied from the code.
- Templates, memory and settings live in Ariya's database and change without a code release. Template content can differ from the [catalog](/documents/template-catalog), so check **Documents → Templates** when it matters.
- Where the in-app help (the **?** panel) disagrees with the app, these pages follow the app and note the difference under **Gotchas**.
